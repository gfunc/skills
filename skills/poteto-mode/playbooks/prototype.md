### Prototype

**You own the design decision, not the code. The prototype is a throwaway instrument. The real build follows Feature.**

The one playbook where the Laziness Protocol's "smallest change" and the verification bar invert. Speed over polish, code quality does not matter, no planning. The rigor is in picking the right design cheaply. Propose variations the user didn't ask for, throw an approach away and try another.

1. Scope the decision the prototype exists to make: which layout, which interaction, which density, or for an empirical fork which behavior, timing, or approach. No decision means no prototype. Route to Feature. The scope also names which kind this is: a **new prototype**, a **revision** of an existing one (same decision, sharper answer), or a **broken artifact** to repair. A revision — and a spec-plus-prototype evolution, where a settled direction updates the owning spec and the artifact together — stays on Prototype even when it adds interactions or user stories. Production behavior goes to **Feature**. A broken artifact that no longer runs or no longer answers its question goes to **Bug fix**.
2. Gather references when the design space is open. Search for prior art, summarize a moodboard of themes, palettes, and layouts, let the user pick directions before building. Skip when the direction is set. A UX direction still open between materially different treatments goes through **Arena** (`skills/arena/SKILL.md`); a direction already settled records one line in the effort's decisions saying why Arena was unnecessary, and reopening the direction returns it to Arena.
3. Build throwaway in the effort tree, `.scratch/<effort>/prototype/<slug>/` in the target repo, separate from production source. For a visual decision, vanilla HTML/CSS/JS or the lightest stack that renders the idea, CDN deps, a dev server with hot reload. For a behavioral or timing decision, the smallest script that exercises the question. No production framework, no tests, no abstractions.
4. When comparing alternatives, build them behind one switcher (buttons or a keypress), each variant labeled. This is the **exhaust-the-design-space** principle skill made cheap.
5. Verify on the matching surface. For a visual decision, screenshot each variant via the control skill and drive the interaction. For a behavioral or timing decision, observe the thing you are deciding by logging the timing, printing the output, or watching the render. The observation is the test here, not an assertion. For a single-file HTML deliverable, open the exact exported file through `file://` and prove it there: a non-empty application mount, no browser console errors, and the selected journeys driven. HTTP evidence does not substitute — it is a different runtime.
6. Present alternatives, tradeoffs, and a recommendation. The output is the decision plus the throwaway artifact, not shippable code. Do not start the full build of the selected direction until independent judging has run (Arena verdict or the fresh judge it spawned), synthesis is recorded, and any operator direction choice the flow requires is made. Capture the decision into the owning effort's `spec.md` and `decisions.tsv` when one exists, otherwise into the real code or decision record, per the prototype skill's completion gate. Later implementation follows an explicit operator invocation of **Feature** (or `architect` for the shape); it is never a continuation of this run.

The build and verify steps above run through the prototype skill's scenario branches: route the input and question by the routing table in `skills/prototype/SKILL.md`, then build and verify on the selected branch file — `skills/prototype/LOGIC.md`, `skills/prototype/VARIANTS.md`, `skills/prototype/DESIGN-DOC.md`, or `skills/prototype/REDLINE.md`. The branch file carries the branch's shape and evidence form; this playbook stays the sequence, the decision, and the reply. The completion gate in `skills/prototype/SKILL.md` is the single authority for runnable, verified, and captured; this playbook adds no second gate.

**Reply:** the variants explored, the evidence (screenshots for a visual decision, the observed output or timing for a behavioral one), tradeoffs, your recommendation, and the scratch path. Say plainly that the prototype is throwaway.
