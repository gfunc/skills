### Prototype

**You own the design decision, not the code. The prototype is a throwaway instrument. The real build follows Feature.**

The one playbook where the Laziness Protocol's "smallest change" and the verification bar invert. Speed over polish, code quality does not matter, no planning. The rigor is in picking the right design cheaply. Propose variations the user didn't ask for, throw an approach away and try another.

Open a todolist with the six numbered steps below verbatim before any task-specific todos. Each step closes only with its named evidence or a one-line `skip: <reason>`. A custom smaller checklist does not execute this playbook.

1. Scope the decision the prototype exists to make: which layout, which interaction, which density, or for an empirical fork which behavior, timing, or approach. No decision means no prototype. Route to Feature. Name the kind: a **new prototype**, a **revision** of an existing one, or a **broken artifact** to repair. A revision and a spec-plus-prototype evolution stay on Prototype even when they add interactions or user stories. Production behavior goes to **Feature**. A broken artifact that no longer runs or answers its question goes to **Bug fix**. For a flow, interaction, or information-architecture decision, establish the intended actor, starting situation, intended outcome, and the task steps crossing the decision under test; derive these from the request, spec, incumbent, and caller context first, and interview only missing product choices. Name the claim to settle, the cheapest adequate fidelity, and what that fidelity cannot establish, and cover all relevant audiences, not only the requester's named surface.
2. For a replacement or migration, apply the prototype skill's incumbent-audit rule before building: audit coverage broadly, then reproduce the selected migration area's equivalent workflows before extending. Gather references when the design space is open. Search for prior art, summarize a moodboard of themes, palettes, and layouts, and present the low-fidelity sketch or direction options for the operator to confirm or redirect. For a UI/UX question this sketch/direction confirmation is a named gate: construction of the selected direction proceeds only after the operator confirms, the confirmed direction and any redirection are recorded in the effort's `decisions.tsv`, and the agent never confirms its own sketch on the operator's behalf. For a behavioral, timing, or logic question with no UI direction to confirm, the gate does not fire. A UX direction still open between materially different treatments goes through **Arena** (`skills/arena/SKILL.md`). When the question is comprehension or flow rather than appearance, frame the Arena with a common task, source-grounded fixture conditions, adequate candidate fidelity, and pre-judge evidence requirements: the coordinator or a separate test seat collects comparable observations before the judge scores, candidate logs demonstrate behavior but not representative-user comprehension, and the judge scores artifacts and evidence independently without becoming a representative user. Keep grade weights hidden; share the task and required deliverable evidence, and repeat the relevant task checks in Phase F after grafting. A direction already settled records one line in the effort's decisions saying why Arena was unnecessary. Reopening the direction returns it to Arena.
3. Before starting a selected full build from Arena, wait for the independent judge's verdict, the synthesis record, Arena Phase F's verification result, and any operator direction choice the flow requires. This wait does not apply when step 2 settled the direction without Arena. Build throwaway in the effort tree, `.scratch/<effort>/prototype/<slug>/` in the target repo, separate from production source. For a visual decision, use vanilla HTML/CSS/JS or the lightest stack that renders the idea, CDN deps, and a dev server with hot reload. For a behavioral or timing decision, use the smallest script that exercises the question. No production framework, tests, or abstractions.
4. When comparing alternatives, build them behind one switcher (buttons or a keypress), each variant labeled. This is the **principle-exhaust-the-design-space** skill made cheap.
5. Verify on the matching surface. For a visual decision, screenshot each variant via the control skill and drive the interaction. For a behavioral or timing decision, observe the thing you are deciding by logging the timing, printing the output, or watching the render. The observation is the test here, not an assertion. For a single-file HTML deliverable, open the exact exported file through `file://` and prove a non-empty application mount, no browser console errors, and the selected journeys. HTTP evidence does not substitute because it is a different runtime.
6. Present alternatives, tradeoffs, and a recommendation. The output is the decision plus the throwaway artifact, not shippable code. Capture the supported conclusion and its unresolved claims into the owning effort's `spec.md` and `decisions.tsv` when one exists, otherwise into the real code or decision record, per the prototype skill's completion gate, distinguishing verified behavior, operator-approved direction, and user observation performed or not. Later implementation follows an explicit operator invocation of **Feature** (or `architect` for the shape); it is never a continuation of this run.

The build and verify steps above run through the prototype skill's scenario branches. Route the input and question by the routing table in `skills/prototype/SKILL.md`, then build and verify on `skills/prototype/LOGIC.md`, `skills/prototype/VARIANTS.md`, `skills/prototype/DESIGN-DOC.md`, or `skills/prototype/REDLINE.md`. The branch file carries the branch's shape and evidence form. This playbook stays the sequence, the decision, and the reply. The completion gate in `skills/prototype/SKILL.md` is the single authority for runnable, verified, and captured; this playbook adds no second gate.

**Reply:** the variants explored, the evidence (screenshots for a visual decision, the observed output or timing for a behavioral one), tradeoffs, your recommendation, and the scratch path. Name the evidence class (verified behavior, operator-approved direction, user observation performed or not) and any unresolved usability claim. Say plainly that the prototype is throwaway.
