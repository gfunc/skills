### Multi-phase or multi-PR plan

Principles: apply the `Verification readiness` and `Dev-lead plan` rows in [§ Principles](../SKILL.md#principles) of the skill.

**You own the plan, not the code. The plan is a checklist an owner runs box by box and the operator audits from the evidence.** The plan is the deliverable. Do not implement.

1. When the change is one or two files with an obvious approach, skip the plan. Say so and stop.
2. Settle open questions by prototype before you write. Run `skills/poteto-mode/playbooks/prototype.md` for each. Keep the branch, the SHA, and the screenshots for Appendix A. For the drivability probe, launch the real app from a clean checkout through the repo's launch or e2e setup and record the command, ready signal, one driven journey, timestamp, and any production boundary that requires a supported seam. A test-only mock does not count. An e2e setup that boots and drives the real surface is the recipe the generated verify skill wraps. Ask the operator only about a product or preference call that no run can settle. Give options (the **never-block-on-the-human** principle skill). Before writing, list every repo, namespace, registry, and credential store the plan's runs may write. Evidence establishes existence and intended effects, not permission. An external, shared, production, or credential-store write needs an operator grant before the plan runs. Never request a secret value. An unconfirmed grant is a refuse-to-plan condition.
3. Explore in research subagents on the profile's Role mapping type, with the [research role prompt](../references/roles/research.md). Give each an explicit model per its Subagents section (the **guard-the-context-window** principle skill). Pick each subagent's reasoning level and fast or standard speed for the job, per that section. Each returns file pointers, conventions, test commands, and entry points. No inlined dumps.
4. Take the main agent's verification readiness decision and evidence as inputs. Stamp the plan with `node skills/start-dev/scripts/emit-plan --feature <slug> --title "<Program>" --surface <surface> --pr <id>`. The script path is relative to the stack root; the stack root is three directories up from this playbook file (`playbooks/` to `start-dev/` to `skills/` to the root), so from any other working directory resolve it from this file's location and invoke the script by its absolute path. The command writes `.scratch/<feature-slug>/plan.md` under the caller's working directory in the target repo, from `skills/start-dev/references/plan-skeleton.md`, with the title, the execution playbook, the swarm-workers model, the PR id, the Surface line, and the standing orders already stamped; the operator may name the output path with `--out`. Record the decision in `## Verification readiness`, filling `Decision`, `Surface`, `Drivability`, `Boundary`, `Evidence`, `Skill`, `Map`, `Formal`, `Formal property`, `Maintenance route`, and `Owner`. Resolve the verify-skill and feature-map paths for `exists`; otherwise name the maintenance route or creation trigger. Append one readiness row to the run root's `decisions.tsv`. Then fill every remaining placeholder box. Decomposition happens here: break the spec into units, one box each, one PR section per PR. One PR is one change with its own evidence (the **sequence-verifiable-units** principle skill). A tracker-visible work-ticket set is optional; write it only on request. Infer each PR section's Surface from what the change touches, `ui`, `cli`, `library`, or `backend`. Set its Change line to `user-facing` by default for `ui` and `cli`, and `internal` by default for `library` and `backend`; classify by observable behavior, not by surface alone. A `Change: user-facing` PR carries a map-update box, while a `Change: internal` PR omits it. Name the execution playbook in **How to read this**. Pick between `skills/poteto-mode/playbooks/autopilot-full.md` and `skills/poteto-mode/playbooks/autopilot-stack.md` per the rule at the end of `skills/poteto-mode/playbooks/autopilot-stack.md`; `autopilot-stack` is the default. A standing program takes `skills/poteto-mode/playbooks/orchestrate.md`.
5. Write under `/technical-writing` in full, then `/unslop`. The body is one Diátaxis mode, how-to. Appendices hold explanation and reference. Each heading states the task or the finding. No long dashes. No mid-sentence colons.
6. Run `node skills/start-dev/scripts/check-plan.mjs <plan.md>` and fix every line it prints (the **encode-lessons-in-structure** principle skill). The script path is relative to the stack root; resolve the stack root from this playbook file's own location, three directories up, and invoke the script by its absolute path when running from anywhere else. The checker validates the readiness section and decision branch, the Change line and map-update box, feature-entry lane tokens, the formal block, and the required creation tasks and gates; satisfy those contracts with real paths and edges. A plan may read the installed plugin instead of `origin/main`; name existing absolute files under `<installed plugin root>/skills/`, and the checker validates them when that plugin is installed.
7. Hand back. Post the plan path, the script's output, and the step table, one row per playbook step. Put every open scope question in the same approval summary as the plan handback, so one approval settles the plan and the questions; ask nothing in a separate round. The summary names the readiness decision, drivability evidence and boundary, verify-skill and feature-map coverage, formal decision and property, and any creation carriers and gates. In that summary, separate material role-model substitutions from product scope and checker exceptions. Name the affected roles, original and replacement models, reason, and effect on model-family diversity. Then stop. Execution starts on the operator's explicit go, under the execution playbook the plan names.

**Verification.** Tests alone are not sufficient verification. A PR is verified only when its unit, live, and perf boxes are all checked (the **prove-it-works** principle skill). That sentence is the verification rule. Every verification block opens with it. The full gate is the PR section's `Verify, unit`, ten `Verify, live` lanes, `Verify, formal`, and `Verify, perf` blocks. The live block is mandatory on every surface, and its shape keys off the PR's Surface line. A `ui` PR runs ten lanes at the PR head that drive the real UI through the control skill, per the **swarm** skill, on the `swarm workers` model read from the brief's `Model: swarm workers=` line, then the active profile's `### Role model table`, then `~/.agents/pstack-models.md`, then the skill's stated default. The lane worker is a runner, not a judge. One asserted subcommand, exit code and evidence paths, with the PR owner applying the predicate. An asserted lane may name a fast-tier `swarm workers` alias; the qualitative lanes keep the verdict with the owner. Each ui lane is one box naming a backticked `<feature-id>#<sub-id>`, one journey under one condition, the screenshot it saves, and its pass predicate. A `cli` PR runs the same ten-lane structure and feature-entry contract, and each lane logs its transcript path with `Log` instead of saving a screenshot. Cover every changed user-facing feature at least once. PR-specific probes add conditions on existing entries; a genuinely new journey gains its feature entry in the same PR. A `library` or `backend` PR runs the unit boxes, at least one live probe box, and the perf block, with no lanes and no review gate. Lane 1 is the **Regression lane against trunk.** It names the load-bearing mapped journey and runs it on trunk and head. If trunk does not have the feature, the lane records that fact and gates the behavior the diff adds plus the end state the user waits for instead of inventing a trunk result. The perf gate is dual-sided. Trunk and head must both produce the named metric. If trunk lacks the feature, also isolate the work the diff adds and set an absolute budget for that work plus the end-to-end state the user waits for. Do not claim a ratio between unlike scenarios. The perf block names the metric, the interleaved probe, the trunk baseline measured first, and the rule with the number that fails. A `ui` or `cli` PR that changes an interaction is review-gated. The operator reviews it in chat with screenshots and a video before merge. A `library` or `backend` PR, and any PR that changes no interaction, writes `**Review gate.** None. <PR id> is not review-gated.` and no boxes under it.

**Creation and formal gates.** For `create-after-first-drivable-batch`, fold a `task:` node into the first wave of the last `ui`/`cli` PR of the first drivable batch; without such a PR, creation stays deferred. For `create-before-amendment`, fold it into the first wave of the amendment's first `ui`/`cli` PR, put `[gate: verification]` after that carrier, and block later `ui`/`cli` PRs on it, not `library` or `backend` PRs. The creation task's lane is the project skill folder glob. `dev-owner` reads and follows `create-verification-skill` by path rather than invoking it through the Skill tool. Its own box carries the prove-once transcript and one mapped feature under `.scratch/<effort>/verification/<pr-id>/`; the skill files merge before the task worktree is removed. The carrier's product changes use the pre-existing drive path and still run ten live lanes; later PRs use the new skill. Every PR carries `**Verify, formal.**` after `Verify, live` and before `Verify, perf`. For `Formal: create` or `exists`, it names the command, property, and covered files/functions. For `Formal: exists-stale`, it names the `maintain-formal-verification-skill` route and owner, then runs the maintained check. For `Formal: not-required`, it says `Not covered.` A PR touching covered code runs the check, and a missing run blocks merge. Fold formal creation into the first PR implementing the covered code after the code is built and before that PR's gate; a dedicated PR is allowed only when no product PR carries the code. Put `[gate: formal]` after the first covered-code PR and block later covered-code PRs on it. A passing check whose model still describes the code advances the sync commit in the same PR; a failure or model mismatch routes to maintenance.

**Maintenance routing.** Verification drift found during the run is routed by cause and scope, never by recreating a skill. In-PR correction when the current PR caused the drift: the map update or formal sync advance lands in that PR. A standalone maintain run when the drift is confined to the verify skill's directory and no product code is involved, at most one PR. A planned feature or its own `/start-dev` run when product code, scope, bounds, or several features are involved: a coupled change joins the current graph, an independent large one gets its own run, and a one-PR maintenance feature uses the PR-owner layer. Record every route as a finding with evidence plus a `decisions.tsv` row naming signal, evidence, route, and owner, and put it in the approval summary so the operator can override it. The main agent or `dev-owner` follows the maintain skill's text by path. The edit scope is the verification skill's own directory only; a product regression becomes a separate bug-fix effort, and the map or property is never weakened to match a broken app.

**Control skill.** Drive through the surface's control skill; on this stack, the project's `verify-<app>` skill, which uses the profile's UI driver. The verify skill wraps the repo's launch or e2e recipe rather than duplicating it, using the detected UI driver (an existing Playwright harness first, then `playwright-cli` (`skills/playwright-cli`) or another browser/CDP recipe) for `ui`, and a tmux/PTY session for `cli`. Read the verify skill and feature map by path. A PR that touches two surfaces gets lanes on both. The arm-the-program re-read box carries the concrete verify-skill and feature-map paths for the program.

The plan skeleton the emitter stamps lives at `skills/start-dev/references/plan-skeleton.md`, next to this playbook. The emitter fills the program title, the execution playbook, the swarm-workers model, the PR id, the Surface line, and the standing orders register from `skills/start-dev/references/standing-orders.md`; the author records readiness and the feature map and fills every remaining placeholder box. Keep every heading and every sub-block in the order the skeleton shows. The surface profiles the checker enforces: `ui` sections carry ten screenshot lanes and `cli` sections ten transcript lanes with `Log` paths, every lane naming a backticked `<feature-id>#<sub-id>`; `library` and `backend` sections carry no lanes and a `**Review gate.** None.` line. The Change line defaults to `user-facing` for `ui` and `cli`, and `internal` for `library` and `backend`. Only `Change: user-facing` sections carry a map-update box. Every section keeps `Verify, formal` in the skeleton's exact order.

**Reply:** the plan path, the PR ids with their dependencies and the review-gated set, the readiness decision and evidence, feature-map coverage and update dispositions, the formal decision and property, creation carriers and gates, what the prototypes proved and what stays unproven, material role-model substitutions and their effect on model-family diversity, and the check script's output.
