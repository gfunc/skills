### Multi-phase or multi-PR plan

Principles: apply the `Dev-lead plan` row in [§ Principles](../SKILL.md#principles) of the skill.

**You own the plan, not the code. The plan is a checklist an owner runs box by box and the operator audits from the evidence.** The plan is the deliverable. Do not implement.

1. When the change is one or two files with an obvious approach, skip the plan. Say so and stop.
2. Settle open questions by prototype before you write. Run `skills/poteto-mode/playbooks/prototype.md` for each. Keep the branch, the SHA, and the screenshots for Appendix A. Ask the operator only about a product or preference call that no run can settle. Give options (the **never-block-on-the-human** principle skill). Before writing, list every repo, namespace, registry, and credential store the plan's runs may write. Evidence establishes existence and intended effects, not permission. An external, shared, production, or credential-store write needs an operator grant before the plan runs. Never request a secret value. An unconfirmed grant is a refuse-to-plan condition.
3. Explore in research subagents on the profile's Role mapping type, with the [research role prompt](../references/roles/research.md). Give each an explicit model per its Subagents section (the **guard-the-context-window** principle skill). Pick each subagent's reasoning level and fast or standard speed for the job, per that section. Each returns file pointers, conventions, test commands, and entry points. No inlined dumps.
4. Stamp the plan with `node skills/start-dev/scripts/emit-plan --feature <slug> --title "<Program>" --surface <surface> --pr <id>`. The script path is relative to the stack root; the stack root is three directories up from this playbook file (`playbooks/` to `start-dev/` to `skills/` to the root), so from any other working directory resolve it from this file's location and invoke the script by its absolute path. The command writes `.scratch/<feature-slug>/plan.md` under the caller's working directory in the target repo, from `skills/start-dev/references/plan-skeleton.md`, with the title, the execution playbook, the swarm-workers model, the PR id, the Surface line, and the standing orders already stamped; the operator may name the output path with `--out`. Then fill every remaining placeholder box. Decomposition happens here: break the spec into units, one box each, one PR section per PR. One PR is one change with its own evidence (the **sequence-verifiable-units** principle skill). A tracker-visible work-ticket set is optional; write it only on request. Infer each PR section's Surface from what the change touches, `ui`, `cli`, `library`, or `backend`. Name the execution playbook in **How to read this**. Pick between `skills/poteto-mode/playbooks/autopilot-full.md` and `skills/poteto-mode/playbooks/autopilot-stack.md` per the rule at the end of `skills/poteto-mode/playbooks/autopilot-stack.md`; `autopilot-stack` is the default. A standing program takes `skills/poteto-mode/playbooks/orchestrate.md`.
5. Write under `/technical-writing` in full, then `/unslop`. The body is one Diátaxis mode, how-to. Appendices hold explanation and reference. Each heading states the task or the finding. No long dashes. No mid-sentence colons.
6. Run `node skills/start-dev/scripts/check-plan.mjs <plan.md>` and fix every line it prints (the **encode-lessons-in-structure** principle skill). The script path is relative to the stack root; resolve the stack root from this playbook file's own location, three directories up, and invoke the script by its absolute path when running from anywhere else. A plan may read the installed plugin instead of `origin/main`; name existing absolute files under `<installed plugin root>/skills/`, and the checker validates them when that plugin is installed.
7. Hand back. Post the plan path, the script's output, and the step table, one row per playbook step. Put every open scope question in the same approval summary as the plan handback, so one approval settles the plan and the questions; ask nothing in a separate round. In that summary, separate material role-model substitutions from product scope and checker exceptions. Name the affected roles, original and replacement models, reason, and effect on model-family diversity. Then stop. Execution starts on the operator's explicit go, under the execution playbook the plan names.

**Verification.** Tests alone are not sufficient verification. A PR is verified only when its unit, live, and perf boxes are all checked (the **prove-it-works** principle skill). That sentence is the verification rule. Every verification block opens with it. The live block is mandatory on every surface, and its shape keys off the PR's Surface line. A `ui` PR runs ten lanes at the PR head that drive the real UI through the control skill, per the **swarm** skill, on the `swarm workers` model read from the models file (`~/.agents/pstack-models.md`). Each ui lane is one box with a concrete scenario, the screenshot it saves, and its pass predicate. A `cli` PR runs the same ten-lane structure, and each lane logs its transcript path with `Log` instead of saving a screenshot. A `library` or `backend` PR runs the unit boxes, at least one live probe box, and the perf block, with no lanes and no review gate. One lane is the **Regression lane against trunk.** It runs the same load-bearing scenario on trunk and head. If trunk does not have the feature, the lane records that fact and gates the behavior the diff adds plus the end state the user waits for instead of inventing a trunk result. The perf gate is dual-sided. Trunk and head must both produce the named metric. If trunk lacks the feature, also isolate the work the diff adds and set an absolute budget for that work plus the end-to-end state the user waits for. Do not claim a ratio between unlike scenarios. The perf block names the metric, the interleaved probe, the trunk baseline measured first, and the rule with the number that fails. A `ui` or `cli` PR that changes an interaction is review-gated. The operator reviews it in chat with screenshots and a video before merge. A `library` or `backend` PR, and any PR that changes no interaction, writes `**Review gate.** None. <PR id> is not review-gated.` and no boxes under it.

**Control skill.** Pick it by surface. Browser, Electron, and web UIs use `control-ui` from `cursor-team-kit`. CLIs and TUIs use `control-cli` from `cursor-team-kit`. Native mobile uses whatever simulator-driving skill the repo has. A PR that touches two surfaces gets lanes on both. A surface with no control skill is a risk in Appendix C, and its live block still names how each lane drives it. This stack's local mapping supersedes the upstream names where they differ: UI surfaces drive through Playwright via `skills/playwright-cli`, and CLI surfaces drive through a tmux/PTY session. The arm-the-program re-read box carries the concrete skill path for the program.

The plan skeleton the emitter stamps lives at `skills/start-dev/references/plan-skeleton.md`, next to this playbook. The emitter fills the program title, the execution playbook, the swarm-workers model, the PR id, the Surface line, and the standing orders register from `skills/start-dev/references/standing-orders.md`; the author fills every remaining placeholder box. Keep every heading and every sub-block in the order the skeleton shows. The surface profiles the checker enforces: `ui` sections carry ten screenshot lanes, `cli` sections ten transcript lanes with `Log` paths, `library` and `backend` sections carry no lanes and a `**Review gate.** None.` line.

**Reply:** the plan path, the PR ids with their dependencies and the review-gated set, what the prototypes proved and what stays unproven, material role-model substitutions and their effect on model-family diversity, and the check script's output.
