### Plan authoring

Principles: apply the `Verification readiness` and `Dev-lead plan` rows in [§ Principles](../SKILL.md#principles) of the skill.

**You own the plan, not the code. The plan is a checklist an owner runs box by box and the operator audits from the evidence.** The plan is the deliverable. Do not implement.

1. **Skip when small.** One or two files with an obvious approach takes no plan. Say so and stop.
2. **Settle open questions by prototype before you write.** Run the prototype playbook for each. Keep the branch, the SHA and the artifacts for Appendix A. For the drivability probe, launch the real app from a clean checkout through the repo's launch or e2e setup and record the command, the ready signal, one driven journey, the timestamp, and any production boundary that needs a supported seam. A test-only mock does not count. Ask the operator only about a product or preference call that no run can settle.
3. **Explore in research subagents.** Each returns file pointers, conventions, test commands and entry points, never an inlined dump. Give each an explicit model.
4. **Take the readiness decision and stamp the shell.** Hand the plan lead the decision and its evidence. Run `emit-plan --feature <slug> --title "<PR title>" --surface <surface> --pr <id>`. The emitter renders from `skills/start-dev/references/plan-shape.mjs`, which is the only statement of the plan's shape; do not restate its blocks in this playbook or in the plan. Record the decision in `## Verification readiness` and append one `decisions.tsv` row.
5. **Derive units from the stories.** Each story is a candidate unit. Split or merge by one test: a reviewer could reject one unit while approving its neighbour. A unit is the smallest item with its own test cycle, its own file lane and its own worktree. Fold setup, scaffolding and documentation into the unit whose deliverable needs them, and batch several small same-shape edits into one unit.
6. **Write the lane table.** One row per unit: id, deliverable, file lane, worktree, scoped test command, budget in whole minutes, dependencies. Two units sharing a lane never run together, and this table is what proves it. Each `Verify, live` lane carries its `Timeout` in whole minutes. Both are checked against the `--spawn-bound` passed to the checker. A Kimi run resolves that number from `KIMI_SUBAGENT_TIMEOUT_MS`, then `[subagent] timeout_ms`, then the 120-minute default, and passes `unlimited` when the resolved value is `0`. The profile states the keys.
7. **Write the run graph.** `unit:` nodes only, each carrying its file lane, plus one `pr:` node and one `[gate: final]`. No wave subgraphs and no per-section gates. Name the critical path, the staffing map and the risk register.
8. **Write the one PR section.** Its blocks come from the shape module. The units live in `Build` with the lane table. `Files` names every file with `Create`, `Edit` or `Delete`, and every path must fall inside some unit's lane. `Verify, unit` carries the scoped test commands. `Verify, live` carries one final-gate lane per changed sub-feature plus the regression journey. `Verify, formal` runs once. `Verify, perf` only for a unit that changes a measured path. `Review gate` names the independent reviewer, the area split above the threshold, and the operator. `Merge` names the landing rule.
9. **Review depth.** Above eight units or 1,500 changed lines, the review gate names one area reviewer per unit group and the aggregating lead. At or below it, one reviewer.
10. **Check.** Run `check-plan.mjs --spawn-bound <minutes|unlimited>` and fix every line it prints. The checker reports every problem with its location, and a missing or unrecognized bound is an error.
11. **Hand back.** Post the plan path, the checker's output and the step table. Then stop. Execution starts on the operator's explicit go, under `skills/start-dev/playbooks/single-pr.md`.

**Verification.** Tests alone are not sufficient verification. A unit is verified when its scoped tests pass in its own worktree, and the PR is verified when the final verify block passes. The unit gate is the scoped tests. The final verify runs the full suite at the merged head, the verify skill's lanes, the formal check where covered, and one independent review that reads the diff and the run's evidence. A red unit gate stops the run.

**No waves.** The plan has no wave section and no wave gate. Order and grouping live in the graph's edges, and parallel work is the ready set of that graph.

**Reply.** The plan path, the checker output, the readiness decision and evidence, the feature-map coverage, the formal decision, the hats in play, and any blocker with its obstacle.
